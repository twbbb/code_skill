你已获得一份规格说明。该规格说明应关联若干工单，描述如何实现该规格。

问题跟踪器应该已经提供给你。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

目标是在单一 **集成分支** 上实现整份规格说明，并以问题跟踪器关闭工作的方式解决每一张工单。

这些工单不是步骤清单。它们是带有阻塞关系的 **任务图**。这意味着始终存在一个可被领取的工单 **前沿**。

与子代理的双向沟通应尽量精简。主要通过 **上下文指针** 沟通：指向规格说明、工单、研究笔记和先前的提交。不要重复指针已能获取的信息。

**实现子代理** 应尽可能在后台运行，以实现最大并发。

## 步骤

1. 阅读规格说明和工单，理解任务图。

2. （可选）使用 **探索子代理** 开展工单所需的任何探索——相关代码库文件或外部文档。确保探索子代理能够保存文件——它应将 markdown 笔记保存在仓库外的目录中，供所有后续子代理访问。这样 **实现子代理** 便可专注于实现而非探索。

3. 创建集成分支。如果问题跟踪器通过 PR 关闭工作，或用户要求创建一个 PR，则在第 5 步首次合并后打开草稿 PR（没有超前于 main 的提交的分支无法打开 PR），并标记为关闭该规格说明和工单。

4. 使用 **实现子代理** 实现每张工单，每个子代理在各自的 worktree 和各自的分支上工作。每个实现子代理：
   - 开始前确认其 worktree 基于集成分支，若不是则重置到该分支；
   - 调用 Skill 工具并传入 `tdd` 以构建该工单；
   - 在报告完成前，将集成分支的最新提交合并到自己的分支

5. **实现子代理** 完成后，用 **合并子代理** 将其工作合并到集成分支。

6. 如果这改变了可用工单的 **前沿**，则启动更多 **实现子代理** 处理新工单。这样可以实现最大并发。

7. 所有工单完成后，在集成分支上调用 Skill 工具并传入 `code-review`。在单个 **实现子代理** 中修复代码审查提出的所有问题。

8. 如果已有草稿 PR，将其标记为可供审查。否则，以问题跟踪器关闭工作的方式解决每张工单，并报告集成分支。

9. 清理所有 **实现子代理** 的 worktree。
