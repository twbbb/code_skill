# 用例文档格式

`<工作区>/<服务目录名>.md`。svc-gen-test-case 写测试前置和用例，svc-local-test 写结果行和执行汇总。照抄样板 `common_server/wxtoken/testcase/wxtoken.md` 的结构。

## 整体

```markdown
# <服务> 本地测试范围

需求：[<需求文档名>](<相对路径>)（一句话说清做什么）。没有需求文档就写「无需求文档，按代码覆盖」。
被测服务：`<仓库>/<服务>`。环境见 env.yaml，执行配置见 cases.yaml，数据脚本在 data/，测试代码在 *_test.go。

## 测试前置
### 代码基线 / 用户确认 / 怎么跑 / 进程 / 兄弟服务 / 外部下游与替身 / 建表/配置要求 / 测试数据 / 流程链路 / 需求覆盖

## <入口分组>        （如 ## GetAccessToken、## 定时刷新）
### NN. <入口>：<标题>

## 执行汇总
```

## 测试前置各节

- **代码基线**：由 `code_impact.py stamp` 写，一行 `` - `<服务>`：`<分支>` @ `<40 位 commit>` ``，有未提交改动时末尾带「（有未提交改动）」。
- **用户确认**：每次确认一行 `- YYYY-MM-DD：<确认了什么>`。
- **怎么跑**：照抄
  ```bash
  localstart/startserver.sh start      # 编译并起本服务和兄弟服务的进程，缺表时先建表
  ./run env                            # 环境自检
  ./run all                            # 或 ./run 01 02a …；新开一轮，证据写到 result/<轮>/
  localstart/startserver.sh stop
  ```
- **进程**：表格 `进程 | 用途 | 配置差异`，默认进程放第一行。同一个服务要用不同配置（定时任务周期 2 秒、进程内缓存 10 秒）就分成不同进程，写清差异。端口由 svc-local-env 分配，写在 env.yaml。
- **兄弟服务**：每个一行 `<服务名>（<目录>）：被调的方法；用它的哪个进程`，没有写「无」。
- **外部下游与替身**：每个外部下游一行 `<host 或 trpc service>：<被调的 path 或方法>`，再加一行 `降级：<真实> → 替身，<原因>`。
- **建表/配置要求**：建表文件、本地配置里必须有的项（如本地专用主密钥）。
- **测试数据**：测试标识前缀；每个标识一行 `<角色>：<标识>，<状态说明>`（角色就是 cases.yaml `accounts` 的键）；全表扫描的用例怎么清别人的行；进程内缓存对重跑的影响。
- **流程链路**：每个入口一条公共链路：
  ```markdown
  - `<接口名>`（`analysis/<接口名>/<ts>.json`）
    1. 节点名：`日志关键字`（文件:行）
    2. 节点名：无日志（文件:行）｜<核对方式：用哪条 SQL、Redis 或替身命中证明这一步>
  ```
  从调用树按执行顺序挑关键节点：入口判断、读到的关键数据、分支决策、写库、下游调用和结果、结束。关键字取节点 `log` 里格式串的固定部分；出处在仓库外的（如 toolbox 打的）写 `（toolbox <路径>:行）`。
- **需求覆盖**：每条需求用例一行 `R<N>：<原文> → 用例 NN、NN` 或 `→ 不覆盖：<原因>`；最后一行列出明确不测的场景和原因。

## 用例

标题 `### NN. <入口>：<标题>`。入口写法：RPC `` `Service.Method` ``（proto 里的 service 名），HTTP `` `HTTP <handler>` ``，定时任务 `` `定时任务 <任务名>` ``。废弃的在标题末尾加「（已废弃）」，序号保留。

```markdown
### 01. `WxToken.GetAccessToken`：Redis 里没有，当场换新
- 进程：wx1                       （默认进程可省）
- 目的：一句话。
- 前置条件：用到的测试标识及其库里、Redis 里的状态；时间写相对执行时的（「剩 5 分钟」）。
- 参数：请求字段；HTTP 写 method、path、header、body。
- 下游返回：兄弟服务写「真实」；外部下游写「替身：<被测服务会发出的请求（method、URL 关键 query、body 关键字段）>，返回 <…>」。
- 预期结果：
  - 响应：返回码、关键字段（定时任务省略）。
  - 状态：核对用的 SQL、Redis 命令和预期值。
  - 流程：这条用例特有的分支节点（如「不换新：`!access_token 已换新`」）。公共链路节点和替身命中由执行时自动核对。
- 结果：通过｜2026-10-24 21:26｜[证据](result/20261024-212559/01_GetAccessToken.md)
```

用例下可能出现的标记行：
- `- 待确认`：本次新加或改了预期，用户还没确认。svc-local-test 跳过它。
- `- 待复核：<原因>`：代码改动或执行时发现预期写错后改过，交给下一步对照产物。
- `- 结果：…`：只保留最新一轮，覆盖上一次的；拆段的每段一行 `- 结果（02a）：…`。没通过的写 `失败`、`阻塞`。

## 执行汇总

按每条用例的最新结果统计全部用例：总数、通过、失败、阻塞；失败和阻塞的清单；降级；**其他发现**（用例预期之外的问题，附代码行）；结果来自哪几轮（链接各轮 `result/<轮>/summary.md`）。
