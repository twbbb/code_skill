# 生成用例文档

术语见 [CONTEXT.md](../../CONTEXT.md)。只用于配置是本地文件、依赖本机 MySQL 和 Redis、能独立起起来的服务；依赖远程配置中心、注册中心才能起来的服务不在此列。

- `<服务>`：被测服务的 go 模块目录（有 `go.mod` 的那一层，如 `common_server/wxtoken`），用户给出。
- `<工作区>`：`<服务>/testcase/`，用例文档是 `<工作区>/<服务目录名>.md`。参考 `common_server/wxtoken/testcase/`，看一份做完的测试工作区。
- 可选输入：需求文档路径（如 `.scratch/<项目>/issues/03-wxtoken.md`），文档里的验收清单就是本次的**需求用例**；指定的入口，只给这几个入口补用例。
- 用例在代码写完以后生成。还没写代码时，先只读需求，告诉用户等代码写完再来。
- 下文 `<脚本>` 指 `<本skill目录>/scripts/`。

## 设计原则

- **兄弟服务真实调用，外部下游走替身**：同一仓库里被调的其他服务（如网关调 auth）在本机真实起起来；微信、谷歌、邮件这类外部下游一律写替身（rpcproxy 缓存文件，见 `toolbox/filter/rpcproxy/README.md`）。替身没有状态，同一份请求永远拿到同一份返回：要下游前后返回不同，就让两次请求不同（如带旧 token 和新 token），做不到时把用例拆成 `NNa`、`NNb` 换替身。一次调用里对同一份请求要两种返回的场景测不了，在「需求覆盖」里写明不覆盖。见 `docs/adr/0001-stateless-stubs-only.md`。
- **测试数据全部合成**：每个被测服务一个测试标识前缀（如 `wx_lt_`），每条用例只用带自己序号的标识（`wx_lt_01`、`wx_lt_06_near`），数据脚本开头先清自己的行和 key。
- **真实路径走不通才降级**：外部下游调不通（要真 secret、IP 白名单）就是降级，在「测试前置」的「外部下游与替身」里写一次 `降级：<真实> → 替身，<原因>`。

## 步骤

### 了解背景

1. 读 `<服务>` 的 `main.go`、`trpc_go.yaml`、配置结构、`sql/` 里的建表文件，有需求文档就读需求文档。列出：
   - 全部入口：`main.go` 注册的 trpc service 的每个方法、HTTP handler、定时任务。用户指定了入口就只取那几个。
   - 每个入口的下游：兄弟服务（本仓库其他模块，写清它的目录和被调方法）、外部下游（host 或 trpc service 名）、表、Redis key。
   - 需求用例：需求文档里的每一条验收项，原文照抄，编上号（`R1`、`R2`…）。

   完成：入口、下游、需求用例三张清单都列出来了。

2. 对每个入口，按 `../svc-interface-analyze/SKILL.md` 拿到与当前代码一致的调用树，多个入口一起分析。
   完成：每个入口在 `<工作区>/analysis/<接口名>/` 下都有 `meta.commit` 与 HEAD 一致的调用树。

3. 对每个定时任务入口，确认是不是按状态或时间扫整张表；是的话，用例前置里写明要清掉其他带前缀的行。确认有没有分布式锁、锁 key 里带不带环境名；多实例要抢锁的场景，用例要起两个实例。对每个入口确认有没有进程内缓存，有的话写清过期时间，重跑同一条用例前要不要重启进程。
   完成：每个定时任务都确认了是否全表扫描、锁 key；每个进程内缓存都写清了过期时间。

### 对照代码改动

用例文档已存在时做这一节，新建文档跳过。

4. 执行 `python3 <脚本>/code_impact.py impact --doc <用例文档>`。它拿文档「代码基线」记的 commit 和当前代码（含未提交改动）比，把改动归到函数和类型上，逐条用例给出判定。按判定处理：
   - **直接命中**、**调用链有改动**：用 `git -C <服务> diff <基线> -- <文件>` 读输出里列出的改动声明，对照用例的预期和流程。行为变了就改用例，在用例下加 `- 待复核：<改动原因>`；行为没变就保持原样。
   - **无改动**：保持原样。
   - **未关联调用链**：按用例正文涉及的入口自己对照。
   输出的「流程链路节点」按第 2 步的新调用树改行号和日志关键字。「不在任何入口调用链上的改动声明」和「非 Go 文件改动」，对照第 1 步的清单，确认新入口、新表、新配置都进了文档。
   脚本报基线 commit 本地不存在时，所有用例都按「调用链有改动」处理。
   完成：判定为直接命中、调用链有改动、未关联调用链的用例都对照过，改了的都标了待复核；输出列出的每个流程链路节点都已更新。

### 编写用例文档

5. 按调用链写用例，覆盖正常路径、边界、状态变化、失败处理（下游报错、下游超时、库或缓存里的脏数据）、幂等、多实例并发、标识隔离（只动自己的行）。需求用例里的每一条都要被某条用例覆盖，或在「需求覆盖」里写明不覆盖的原因。
6. 用例全文档统一两位序号（`01`、`02`…），序号是数据脚本、test 函数、证据文件的共同主键，生成后不再改号；删掉的用例保留序号，标题后加「（已废弃）」。一条用例要多次调用、中间改数据或换替身时，拆成 `NNa`、`NNb`。
7. 每条用例一个 `### NN. <入口>：<标题>`，入口写法：RPC `` `Service.Method` ``（proto 里的 service 名，如 `WxToken.GetAccessToken`），HTTP `` `HTTP <handler>` ``，定时任务 `` `定时任务 <任务名>` ``。下面写：
   - 进程：在哪个进程上执行（进程名在「测试前置」的「进程」里定义）。默认进程可以不写。
   - 目的：一句话。
   - 前置条件：用到的测试标识，以及它们在库里、Redis 里的状态。时间写相对执行时的（「剩 5 分钟」「10 秒前过期」）。
   - 参数：请求字段；HTTP 写 method、path、header、body。
   - 下游返回：兄弟服务写「真实」；外部下游写「替身：<返回>」，并写出被测服务会发出的请求（method、URL 和关键 query、body 关键字段），执行时替身命中就证明请求对了。
   - 预期结果，分三部分：
     - 响应：返回码、关键字段。定时任务没有响应，不写。
     - 状态：核对用的 SQL、Redis 命令和预期值。
     - 流程：这条用例特有的分支节点（如「不换新：`!access_token 已换新`」），公共链路上的节点不重复写。替身命中不用写，执行时会按写过的替身自动核对。
8. 文档开头写「## 测试前置」，下面各节：
   - **代码基线**：第 11 步由脚本写，不手写。
   - **用户确认**：第 12 步写。
   - **怎么跑**：照抄下面这段。
     ```bash
     localstart/startserver.sh start      # 编译并起本服务和兄弟服务的进程，缺表时先建表
     ./run env                            # 环境自检
     ./run all                            # 或 ./run 01 02a …；新开一轮，证据写到 result/<轮>/
     localstart/startserver.sh stop
     ```
   - **进程**：表格，每个进程一行：`进程 | 用途 | 配置差异`。默认进程放第一行。同一个服务要用不同配置（如定时任务周期 2 秒、进程内缓存 10 秒）就起不同的进程，配置差异写清楚。端口由 svc-local-env 分配，这里不写。
   - **兄弟服务**：每个一行：`<服务名>（<目录>）：被调的方法；用它的哪个进程`。没有就写「无」。
   - **外部下游与替身**：每个外部下游一行：`<host 或 trpc service>：<被调的 path 或方法>`，加一行降级说明。
   - **建表/配置要求**：用到的建表文件、本地配置里必须有的项（如本地专用的主密钥）。
   - **测试数据**：测试标识前缀；每个测试标识一行 `<角色>：<标识>，<状态说明>`（角色写进 `cases.yaml` 的 `accounts`）；全表扫描的用例怎么清别人的行。
   - **流程链路**：每个入口一条公共链路，第一行 `` - `<接口名>`（`analysis/<接口名>/<ts>.json`） ``，下面从调用树里按执行顺序挑出关键节点：入口判断、读到的关键数据、分支决策、写库、下游调用和结果、结束。每个节点一行 `  N. 节点名：` + `` `日志关键字` `` + `（文件:行）`，关键字取节点 `log` 里格式串的固定部分；节点没有日志，或日志打不出判断要用的字段时，写 `  N. 节点名：无日志（文件:行）｜<核对方式>`，核对方式写用哪条 SQL、Redis 或下游请求证明这一步。不为测试补日志。
   - **需求覆盖**：有需求文档时，每条需求用例一行：`R<N>：<原文> → 用例 NN、NN` 或 `→ 不覆盖：<原因>`。没有需求文档时写「无需求文档，按代码覆盖」，并列出明确不测的场景和原因（如「Redis 不可用：本地没法只停 Redis 不停别的」）。
9. 写入 `<工作区>/<服务目录名>.md`，按入口分组（`## GetAccessToken`、`## 定时刷新`…），文末留 `## 执行汇总`（svc-local-test 填）。
   文档已存在时做增量更新：保留已有用例和它们的结果行，追加新用例，只修改第 4 步判定受影响的用例；标了待复核的交给 svc-local-test 判断对应的数据脚本和 test 代码是否要跟着改。
10. 自检：每条用例都有进程（或用默认进程）、前置、参数、下游返回、预期（响应、状态、流程）；每个外部下游的调用都写了替身；每个需求用例都有覆盖或原因；流程链路每个节点都有日志关键字，或「无日志」和核对方式。
11. 执行 `python3 <脚本>/code_impact.py stamp --doc <用例文档>`，把「代码基线」写成被测服务当前的分支和 HEAD，有未提交改动时会注明。
    完成：「代码基线」里的 commit 是当前 HEAD。

### 和用户确认

12. 把测试范围发给用户确认：每条用例一行 `序号｜入口｜标题｜进程｜替身`，加上兄弟服务、降级、需求覆盖里不覆盖的条目。等用户回复，按回复改文档；没确认之前不交给 svc-local-test。
    - 新建文档：确认后在「用户确认」一节写 `- 用户已确认测试范围：YYYY-MM-DD`。
    - 增量更新：本次新加或改了预期的用例，标题下加一行 `- 待确认`；用户确认后删掉这些行，在「用户确认」一节追加一行日期和本次确认的用例号。
    完成：用户确认过；文档里没有 `- 待确认`。

## 完成

文档的「代码基线」是当前代码，「用户确认」有记录；每条用例都有序号、入口、前置、参数、下游返回、预期（响应、状态、流程）；需求用例都有覆盖或原因；每个入口都有当前的调用树和流程链路。告诉用户下一步：按 `../svc-local-env/SKILL.md` 准备环境，再按 `../svc-local-test/SKILL.md` 执行。
