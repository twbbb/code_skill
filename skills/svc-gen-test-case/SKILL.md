# 生成用例文档

先读 [约定](../svc-local-test-flow/CONVENTIONS.md)。用例文档格式见 [CASE-DOC.md](CASE-DOC.md)。`<脚本>` 指 `<本skill目录>/scripts/`。

输入：`<服务>`；可选需求文档路径（如 `.scratch/<项目>/issues/03-wxtoken.md`，里面的验收清单就是**需求用例**）；可选几个入口，只给它们补用例。用例按写完的代码生成：代码还没写时，读完需求就告诉用户代码写完再来。

## 步骤

1. **列清单**：读 `<服务>` 的 `main.go`、`trpc_go.yaml`、配置结构、`sql/` 建表文件，有需求文档就读需求文档。
   完成：三张清单——
   - 入口：注册的每个 trpc 方法、HTTP handler、定时任务（指定了入口就只取那几个）。
   - 每个入口的下游：兄弟服务（目录、被调方法）、外部下游（host 或 trpc service）、表、Redis key。
   - 需求用例：每条验收项原文照抄，编号 `R1`、`R2`…

2. **拿调用树**：所有入口一起按 `../svc-interface-analyze/SKILL.md` 分析。
   完成：每个入口在 `<工作区>/analysis/<接口名>/` 下有 `meta.commit` 与 HEAD 一致的调用树。

3. **摸清会串的状态**：每个定时任务：是否按状态或时间扫整张表（扫的话前置要清掉其他带前缀的行）、分布式锁 key 带不带环境名（同时起的 RPC 进程和定时任务进程要用不同环境名）、多实例抢锁要不要起两个实例。每个入口：有没有进程内缓存、多久过期、重跑前要不要重启进程。
   完成：每个定时任务的扫表方式和锁 key、每个进程内缓存的过期时间都写进了草稿。

4. **对照代码改动**（用例文档已存在时）：执行 `python3 <脚本>/code_impact.py impact --doc <用例文档>`，按每条用例的判定处理：
   - **直接命中**、**调用链有改动**：`git -C <服务> diff <基线> -- <文件>` 读输出列出的改动声明，对照用例的预期和流程。行为变了就改用例，加 `- 待复核：<改动原因>`；行为没变保持原样。
   - **未关联调用链**：按用例正文涉及的入口自己对照。
   - **无改动**：保持原样。
   - 基线 commit 本地不存在：全部按「调用链有改动」处理。

   输出的「流程链路节点」按第 2 步的新调用树改行号和日志关键字；「不在任何入口调用链上的改动声明」「非 Go 文件改动」对照第 1 步清单，把新入口、新表、新配置补进文档。
   完成：前三种判定的用例都对照过，改了的都标了待复核；输出列出的每个流程链路节点都已更新。

5. **写用例文档**：按 [CASE-DOC.md](CASE-DOC.md) 写进 `<用例文档>`。
   - 按调用链覆盖：正常路径、边界、状态变化、失败处理（下游报错、超时、库或缓存里的脏数据）、幂等、多实例并发、标识隔离。
   - 一次调用里对同一份请求要两种下游返回的场景，替身做不到，写进「需求覆盖」的不测场景。
   - 新用例的序号接在已有的后面；已有用例和它们的结果行原样保留，只改第 4 步判定受影响的。
   完成：每条用例都有入口、前置、参数、下游返回、预期（响应、状态、流程）；每次外部下游调用都写了替身的请求和返回；每条需求用例都有覆盖或原因；流程链路每个节点都有日志关键字，或「无日志」和核对方式。

6. **记基线**：`python3 <脚本>/code_impact.py stamp --doc <用例文档>`。
   完成：「代码基线」的 commit 是当前 HEAD。

7. **用户确认**：把测试范围发给用户，每条用例一行 `序号｜入口｜标题｜进程｜替身`，加上兄弟服务、降级、不覆盖的需求用例和不测场景。等用户回复，按回复改文档。
   - 新建文档：确认后在「用户确认」写一行日期和「确认测试范围」。
   - 增量更新：本次新加或改了预期的用例，标题下先加 `- 待确认`；用户确认后删掉，在「用户确认」追加一行日期和确认的用例号。
   完成：用户回复确认；文档里没有 `- 待确认`。这是进入 svc-local-env 的闸门。
