# 单服务本地测试

先读[约定](CONVENTIONS.md)。每个阶段照对应技能的 SKILL.md 做完，满足它的「完成」再进下一阶段。

输入：`<服务>`（用户没给就问）；可选需求文档路径、指定的入口或用例序号。

## 选路线

看 `<工作区>` 现状，三条路线选一条，告诉用户走哪条：

| 现状 | 路线 |
|---|---|
| 没有 `<用例文档>` | **新建**：阶段 1 → 2 → 3 → 4 |
| 有 `<用例文档>`，被测服务代码比「代码基线」新，或用户要补用例 | **同步**：阶段 1（增量）→ 2 → 3 → 4 |
| 有 `<用例文档>`，代码没变，用户只要执行或重跑 | **重跑**：阶段 3 的检查 → 4 |

代码有没有变：`python3 ../svc-gen-test-case/scripts/code_impact.py impact --doc <用例文档>` 输出「没有改动」就是没变。

## 阶段

1. **生成用例**：按 [svc-gen-test-case](../svc-gen-test-case/SKILL.md) 第 1–6 步（它会调用 [svc-interface-analyze](../svc-interface-analyze/SKILL.md) 拿调用树）。同步路线从它的第 4 步「对照代码改动」开始判定影响。
   完成：`<用例文档>` 写好，「代码基线」是当前 HEAD。

2. **用户确认**：svc-gen-test-case 第 7 步。这是一道闸门：把测试范围发给用户，**停下等回复**，按回复改完、记下确认，才进阶段 3。
   完成：「用户确认」有本次记录，文档里没有 `- 待确认`。

3. **准备环境**：按 [svc-local-env](../svc-local-env/SKILL.md)。已经有 `env.yaml` 的，只补用例文档里新出现的进程、兄弟服务，标准脚本跑一次同步；接入 rpcproxy 要改业务代码，照它第 2 步先给用户看 diff、确认后单独提交。
   完成：`./run env` 全部 ✅。

4. **执行取证**：按 [svc-local-test](../svc-local-test/SKILL.md)。同步路线默认跑全部用例做回归，标了「待复核」的先按它的第 2 步处理产物。
   完成：本轮每条用例都判定了通过、失败或阻塞，用例文档的结果行和执行汇总已更新，进程已停。

## 收尾

向用户汇报：走的路线；新增或改动的用例；分到的端口、改了的业务代码和 commit（若有）；本轮执行汇总、失败定位、阻塞原因和待决定事项、其他发现。提交由用户决定，除了 svc-local-env 接入 rpcproxy 那一次。
