# 证据文件

一条用例在一轮里的完整记录：`result/<轮>/NN_<method>.md`，同目录另有全量日志 `NN_<method>.log`。拆段用例每段各一份。证据文件是判定的唯一依据：核对表里的每个结论都要落在文件里的一段原始输出上。

## 分段和写入方

`run_case.py` 建文件时生成全部分段，其他内容按下表写入。原始输出只由脚本和 `kit_test.go` 写，agent 只填判定类内容。

| 分段 | 内容 | 写入方 |
|---|---|---|
| 头部 | 用例、轮次、requestId、关联 requestId、执行时间、判定 | 脚本生成；`Case.AddRequestID` 加关联 requestId；agent 填「判定」 |
| 前置核对 | 数据脚本执行后、发请求前的状态快照 | `cases.yaml` 的 `pre` |
| 请求、响应 | 每次调用一块，先一行「接口：」，再贴请求原文和响应原文 | `Case.Record`、`Case.HTTP` |
| 替身 | 本条写的每份替身：文件名、对应的下游调用、文件内容 | `Case.StubRPC`、`Case.StubHTTP` |
| 流程链路 | 每个关键节点命中的日志行；每份替身自动有一个「替身命中」节点 | `run_case.py`；agent 把「结论：待填」改成 ✅、❌ 或「无日志」 |
| 核对表 | 前置条件和预期结果拆成的检查项 | agent，用 `evidence.py judge` |
| 原始输出 | go test 输出、执行后的 SQL/Redis、本条的 rpcproxy 日志 | `run_case.py` |
| 说明 | 降级、本轮修了什么、失败定位 | agent |

## 请求

读者只看这一段就要知道调的是哪个接口。每块以「接口：」开头：RPC 写 `Service/Method`；HTTP 写 `METHOD path（进程）`。定时任务没有请求，写一块「接口：定时任务 <任务名>（进程）」说明怎么触发的。

## 流程链路

节点取自用例文档：「测试前置」里该入口的公共流程链路，加上这条用例「预期结果-流程」里的分支节点，写在 `cases.yaml` 的 `flow`。只取本条 requestId（含关联 requestId、`also`）的日志，每个节点最多贴 5 行，其余在 `.log` 里。

用例文档里标了「无日志」的节点不写进 `flow`，按它写的核对方式在核对表里用状态核对。节点没命中，或命中的日志不足以判断时，结论写「无日志」，同样改用状态核对，不改业务代码补日志。

「替身命中」节点没命中，说明被测服务实际发出的请求和写替身时给的请求不一样：看「原始输出」里 rpcproxy 日志的 `cache|miss|<另一个文件>`，对照代码找出差在哪。属于替身请求写错就改 test 代码重跑，属于代码行为不符就判失败。

## 核对表

一行一个检查项：`| 检查项 | 预期 | 实际 | 结论 | 原始输出 |`。

- 预期：按执行时间换算成实际的时间戳，不写相对时间。
- 实际：从原始输出里抄，不改写。
- 原始输出：写对应段落的标题（如「前置核对 Redis」「流程链路 换新」「替身 http.api.weixin.qq.com…json」）。
- 用例文档「预期结果」的响应、状态、流程里的每一条，以及前置核对的每一项，都在核对表里有一行。

## 完成

- 头部和流程链路里没有「待填」。
- 「请求」段每块都以「接口：」开头。
- 核对表覆盖了用例的全部预期和前置。
- 每一行的「原始输出」都能在本文件里找到。
- 没有密钥、密码原文（`evidence.py summary` 会查）。
